# A conversation-agent implementation

The boundary is browser → authenticated chat API → configured model planner → authenticated MCP client → existing server/storage/rules. Model output never supplies household identity or write retry keys. Client-selected cats are checked against authenticated discovery; ambiguous/unselected cats cannot receive guessed writes. Generated tool schemas retain MCP's event-detail validation but omit server-owned event_id/source/idempotency_key. A continue_event flag requests supplementation of the server-stored pending event; the server verifies cat/type/tool and restores the exact event/source. New observations receive new IDs; health unknowns remain unknown. Event detail_evidence must quote the current user input for each supplied non-null field; unsupported fields are omitted before MCP and trigger its missing-detail follow-up. Explicit times likewise require occurred_at_evidence. Evidence fields are agent-only and never persisted as event details. Boolean details additionally require recognized affirmative/negative phrases supporting the value in both the quote and full current message; unrelated quotes, negation fragments and conflicting statements remain unknown. Unsupported wording triggers clarification. Reporter requires a user quote containing the supplied name. Categorical details require explicit recognized phrases for the chosen value. Numeric weight/duration details require the same number with kg/hour units in the quote; free-text values must appear in it. Unrecognized paraphrases remain unknown and trigger follow-up. These conservative checks reduce fabricated defaults; semantic interpretation still needs real-model evaluation and is not a general natural-language proof.

server/models.py wraps AWS Bedrock Converse with its documented toolUse/toolResult flow. No model ID is guessed. Set CAT_NANNY_BEDROCK_MODEL_ID and AWS_DEFAULT_REGION and configure authorized AWS credentials. The chosen model/inference profile must support tool use. IAM needs bedrock:InvokeModel on that authorized resource. No IAM, cloud resources or paid model calls have been created by this implementation. [AWS Converse documentation](https://docs.aws.amazon.com/boto3/latest/reference/services/bedrock-runtime/client/converse.html) and [client-side tool use](https://docs.aws.amazon.com/bedrock/latest/userguide/tool-use-client-side.html) informed the adapter. Provider selection was requested; Bedrock is the implemented initial adapter in line with the project's AWS plan.

server/mcp_client.py uses the official MCP ClientSession and Streamable HTTP client. It initializes, discovers schemas and calls tools over HTTP. The configured canonical URL is server-owned; remote URLs require HTTPS and cannot contain credentials/query tokens. Redirects are disabled. The authenticated development bearer is forwarded solely as an Authorization header, not to the model or conversation database.

server/conversations.py persists household-scoped history, pending follow-up, selected cat, message input/reply, exact model-selected tool plans, prepared arguments and completed tool results. The request/message ID is stable for retries; changed input with the same ID returns409. Completed replies replay from the journal. One turn holds a bounded 300-second lease; an active concurrent turn is rejected. After a crash/timeout the same message can resume once the lease expires (or immediately after a caught failure releases it). Each prepared write has a deterministic session/message/step key; if a write succeeded but its response was lost, MCP's existing receipt returns the original event. Model failure after completed tools preserves those results and safety text in a503 response. The caller retries the same ID rather than sending a new observation. Failed/unresolved turns block newer turns until recovery. The journal is not an exactly-once guarantee for arbitrary external side effects; it relies on MCP mutation idempotency and the existing notification ledger.

Agent loops are bounded to six model rounds and twelve tool calls. Mandatory rule wording is inserted before ordinary model text, with truthful notification acceptance/failure/outcome statements and care confirmation notes. The server presents the first missing-detail question. Model text remains generated and unreviewed; rules and structured evidence remain authoritative. No medical diagnosis capability or model-generated clinical validation is claimed.

Chat HTTP supports both C's /api/chat/session + /api/chat aliases and explicit create/get/message session endpoints. Login verifies the independent CAT_NANNY_CHAT_PASSWORD and exchanges it for a random HttpOnly SameSite=Strict cookie; login handles are in process memory, so re-login is required after restart. Conversation history survives. Origin/Host checks reject cross-origin API use and unexpected hosts. Static page/resources have no bearer tokens; all browser writes require cookie login; arbitrary bearer headers are not accepted. The service rejects production mode because production OAuth/shared storage are not configured.

Verification: tests/test_agent.py exercises the official MCP SDK over actual ASGI HTTP transport, recorded follow-up identity across store restart, exact completed replay, ambiguous accepted-write recovery, model failure after a health warning, household isolation, concurrent leases, model-owned-field rejection, Bedrock request/response shape with a stub client, cookie login and browser API aliases. These tests use a scripted model. C separately exercised the browser login, Today card, recording, supplementation and Vet card against a disposable synthetic backend and real HTTP MCP. This is local integration evidence, not a real Bedrock inference, genuine Alexa call, remote deployment or real SMS delivery.

Remaining: configure and verify the real chosen model/region/permissions; evaluate diverse natural-language prompts (including ambiguous cats, unrecognized times and new-event-versus-follow-up intent); production identity/shared session storage; remote latency and failure verification. Context history is retained without automatic summarization; long conversations can exceed provider context limits and require starting a new conversation. No background recovery worker is implemented.


QA corrections (2026-10-12): supported today/now expressions resolve to the server clock, ignoring model-supplied dates. Fully specified ISO timestamps resolve from the user's quote; ambiguous historical/date-only expressions and future times require clarification before writing. The model receives current household-local time. Enum evidence rejects negated or conflicting assertions in the full current input. Model cat IDs must match the selected cat, including other discovered household cats. Missing questions are a persisted FIFO queue: pending_follow_up remains the active entry for browser compatibility and pending_follow_ups exposes all outstanding events. Completing an entry advances to the next without dropping unrelated questions. Existing single-entry persisted sessions migrate when loaded. Rejected batches retain completed toolUse/toolResult pairs in model history and omit unexecuted calls; replay remains cached. Regression coverage includes warning-window dates, appetite negation, wrong-cat writes, queued follow-ups across restart, and partial-batch history/replay.


Household recorder selection is trusted chat input validated against server configuration and journaled in the request fingerprint. It is excluded from model-writable tool schemas and injected into prepared writes. A separate performed_by_evidence quotes an explicit supported care action by a named person (or “I” referring to the chosen recorder). The demo planner extracts those names and supports basic feeding amount/food phrases. Recorder choice is optional for queries and required for chat event mutations; standalone MCP callers may provide the new attribution fields directly under household authentication.
