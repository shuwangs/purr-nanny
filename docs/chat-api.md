# Chat API handoff for C (A owns server implementation)

Development entry: `server.chat_app:create_app`, separate ASGI server port 8001; MCP server continues on 8000. JSON requests require the HttpOnly chat cookie. The server resolves CAT_NANNY_CHAT_MCP_TOKEN against the existing trusted household/timezone mapping. No anonymous writes or model-defined household identity. C owns web/chat/* assets; A will serve web/chat/chat.html at / when available. Browser assets must not contain embedded bearer tokens; ask for the independent chat password and clear the input after login. Do not call Bedrock/OpenAI from the browser.

- POST /api/chat/sessions, body {} → {schema_version:'1.0', conversation_id}
- GET /api/chat/sessions/{conversation_id} → {schema_version,conversation_id,messages:[{message_id,role,text,status?}],pending_follow_up,tool_results}
- POST /api/chat/sessions/{conversation_id}/messages, body {message_id:string,text:string} → {schema_version,conversation_id,message_id,status,reply,tool_results:[{name,is_error,structuredContent}],pending_follow_up}
- message_id is a client-generated UUID, stable for retries. A repeat with changed text returns HTTP409 message_conflict. Concurrent turn returns409 conversation_busy. Foreign/unknown session returns404. Invalid body400. Provider unavailable503; prior tool results/warnings remain in response when possible. Completed replay returns cached response without rerunning tools/model.

Render reply as text (never HTML). Structured results are authoritative; C may pass get_today/get_vet_summary structuredContent to existing resource views. Show is_error and preserved safety signals, plus follow-up prompts. A inserts mandatory warnings before conversational text, retains unknown values, and reports provider acceptance separately from delivery. pending_follow_up={tool,cat_id,event_id,event_type,source,questions} or null. Model can discover cats via list_cats and must clarify ambiguity before logging. No direct user JSON editing is required in the chat UI.

The API retains durable conversation state and journals each tool action. Stalled/crashed turns are recoverable on the same message_id after a bounded lease; saved tool plans retain stable server-generated write keys. No periodic background notification worker or public deployment is claimed.

C compatibility clarification: A will also provide GET /api/chat/session (returns cats and current conversation_id) and POST /api/chat with {message,cat_id?,request_id,conversation_id?}, returning {reply,conversation_id,results:[{tool,structuredContent,is_error}],follow_up,status}. C can use these aliases. Use POST /api/chat/login {password} once for CAT_NANNY_CHAT_PASSWORD; CAT_NANNY_CHAT_MCP_TOKEN is configured only on the server; it establishes an HttpOnly SameSite=Strict local cookie, so subsequent browser requests need no bearer storage. No credentials are embedded in HTML. GET /apps/today.html and /apps/vet-summary.html return resource_html output for iframe integration. The underlying MCP bearer never enters browser login or chat payloads. Session cookie storage is process-local; after restart sign in again while persisted conversation state survives. Browser tool execution still uses authenticated MCP, never direct repository access.

Implementation ready: compatibility aliases, login/logout cookie routes, static assets and both card routes are implemented in server/chat_app.py. Start the entry on 8001 and keep MCP on 8000. Cookie logins intentionally expire on process restart. The canonical session GET endpoint returns durable messages and latest tool results for history recovery. Alias calls without conversation_id derive a persisted session from the household/request_id so a first-message retry also remains idempotent.

Model setting: CAT_NANNY_BEDROCK_MODEL_ID identifies a tool-capable Bedrock Converse model or inference profile; AWS_DEFAULT_REGION and authorized AWS credential chain are required. No model ID is set in this session; natural-language model access is not yet live-verified. With no model configured, API returns503 model_unavailable and an explicit setup message; it never pretends a chat response was generated. Agent tests use a scripted provider and the real MCP SDK/HTTP service.

Follow-up reply includes the first pending question plus safety notices. Frontend should prefer that question for a one-at-a-time exchange; pending_follow_up retains all missing fields internally. On model failure after a tool completed, retry_required response preserves mandatory warnings and tool results. Retrying the exact same message resumes the persisted plan, not a fresh model-selected write. A different message waits until the original turn has completed/recovered. Development SQLite state is for a single host, not a multi-replica production session service.


Recorder attribution: GET /api/chat/session returns recorders from CAT_NANNY_CHAT_RECORDERS (default Shu/Alex/Yuan). Both message routes accept recorded_by; the chat server validates it against that household's configured list and inserts it into MCP event writes independently of model output. Writes without a selected recorder return recorder_selection_required before mutation; queries remain household-wide and need no selection. The selected name participates in the retry fingerprint and cannot be changed on a replay. The model cannot supply recorded_by. performed_by is separate, explicitly supported care-actor evidence; it does not default to the recorder. Legacy reporter retains its older meaning and is displayed as Reported by.

SQLite persists recorded_by (latest entry), first_recorded_by and entry_history for each distinct accepted mutation, while supplementation preserves performed_by unless explicitly updated. Idempotency replay does not append another history entry. The UI labels care performer and recorder separately and shows original/latest entry attribution after supplementation by another person. Existing records with no attribution stay unknown; no automatic backfill guesses a person.
