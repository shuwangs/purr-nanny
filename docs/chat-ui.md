# Web chat and existing cards — C

C owns apps/chat.html, chat.css, chat.js and the existing view renderer. A owns server/chat_app.py, model adapters, MCP execution, trusted identity and conversation persistence. B owns data and deterministic rules. The UI runs locally with the service; no independent hosted Site is needed for this project increment.

The entry page is served at `/` by `server.chat_app:create_app`; static CSS/JS are `/chat-assets/chat.css` and `/chat-assets/chat.js`. Login uses `/api/chat/login` with a separate chat password to establish A's HttpOnly local session cookie. The password is cleared from the field after submission and is never placed in chat/model payloads. The MCP token is configured and resolved on the server; the page has no MCP token input. Browser calls use same-origin credentials. Model keys and MCP bearer credentials stay on the server. This is development authentication, not production account linking.

GET `/api/chat/session` supplies household cat profiles. POST `/api/chat` accepts message, selected cat_id, optional conversation_id and a UUID request_id. A resolves identity and validates cat selection. Reply text is rendered with textContent. Structured safety signals render before ordinary reply text, ordered emergency, urgent, warning, regardless of whether conversational prose includes them. Results retain notification limitations, sample labels, tool errors and follow-up questions. The frontend performs no symptom interpretation or tool selection.

Today and veterinary results embed the existing `/apps/today.html` and `/apps/vet-summary.html` resources in sandboxed `allow-scripts` iframes. The host completes MCP Apps initialization and passes the exact structuredContent to the renderer. Messages are accepted only from registered card windows. The card reports its content height using the official `ui/notifications/size-changed` message; the host bounds iframe height. The iframe has no same-origin permission or tool-write capability. Reference: https://apps.extensions.modelcontextprotocol.io/api/interfaces/app.McpUiSizeChangedNotification.html .

Interactions: select cat, free-text message, Enter to send, Shift+Enter for newline, conversation starters, Today/Veterinary shortcuts, new conversation and same-ID retry. Sending locks cat selection and concurrent input. Failed requests retain the original ID and selected cat; reconnect preserves the pending request. A new conversation clears displayed messages and pending frontend context while care records remain stored. Follow-up answers use the server conversation ID so A can update the original event.

Verification: tests/test_chat_ui.py runs the Node chat harness (authentication, retry identity, conversation ID, safe text, card source filtering and handshake). Existing renderer tests verify card safety. Browser integration and A's HTTP tests should be recorded separately; a mocked transport is not evidence of live model access.

## Credential and safety requirements — 2026-10-12

The browser submits only a separate chat password, never the MCP bearer or model credentials. A verifies CAT_NANNY_CHAT_PASSWORD and resolves CAT_NANNY_CHAT_MCP_TOKEN server-side. Message UUIDs come from crypto.randomUUID; retries reuse the unchanged ID. A generates each tool-write key from its persisted conversation/message/call identity and rejects model-supplied keys. Missing details must remain null/absent and produce server-defined follow-up; prompting alone is not a guarantee that facts were stated. A owns the provenance enforcement. The UI does not convert missing answers to false or synthesize details.

Frontend regression evidence: tests/chat_ui.cjs verifies an emergency appears before urgent guidance, ordinary reply and follow-up even when prose omits warnings; login body contains password only; token field is absent; repeat sends retain the original request ID.

Updated credential/safety browser evidence: separate chat-password login verified against A's real HTTP service with the MCP token supplied only to build_chat_app server configuration. A synthetic straining/no-urine observation produced a structured emergency box above narrative text. Screenshot: chat-safety.png. No live model calls were used. The full shared suite reached 84 passing tests while A continued strengthening field-value provenance; unsupported wording is deliberately kept unknown rather than inferred.

Final local check for this requirement: 96 tests passed, with the existing Starlette/httpx deprecation warning. A now checks Boolean, enum, numeric/unit and explicit text support before allowing event details; unsupported model values are omitted so the backend can ask missing-detail questions.
